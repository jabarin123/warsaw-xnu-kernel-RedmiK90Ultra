## 3. v93：`-buffer` 与写回（已真机验证）

上游根因：`IconRendering.HardwareTexture` 对纹理底下的 `MTLBuffer` 取弱引用，nil 时
`brk #1`；驱动 `-buffer` 恒为 nil，结果也不拷回 buffer。

我们这边的事实：`redwoodmetal_texture.inc` 原本就是 `- (id)buffer { return nil; }`，
而 mesa 库里 `rwa_buffer_textures_refresh` / `rwa_buffer_textures_writeback` **早就实现了**
（前者每次 commit 前调用，后者从未被调用）。

改动四个文件：

| 文件 | 改动 |
|---|---|
| `redwoodmetal.m` | 纹理类加 `_buffer` / `_bufferOffset` / `_bufferBytesPerRow` 与 `redwoodSetBuffer:offset:bytesPerRow:`；`newTextureWithDescriptor:offset:bytesPerRow:` 创建后把 buffer 交给纹理 |
| `redwoodmetal_texture.inc` | `-buffer` / `-bufferOffset` / `-bufferBytesPerRow` 返回真实值；`dealloc` 在 texture 之后 release buffer |
| `redwoodmetal_mesa.inc` | 解析 `rwa_buffer_textures_writeback` |
| `redwoodmetal_commandbuffer.inc` | `-waitUntilCompleted` 在 fence 成立后调用写回 |

顺带修了一个兼容问题：CI 从上游 userland 现 clone，上游 11-15 把
`struct rwa_stitch_node` / `rwa_linked_function` 挪进了 `tools/mesa/air/air_metal_copy.h`，
与我们驱动自己的定义冲突（`redefinition`），且该头不声明 `writeback`。现在
`redwoodmetal_mesa.inc` 自己写函数原型，不再 include 上游那个头。

真机结果（`once-v93`，`fastboot boot`，未 flash）：

- `Early boot complete`、`display 1280x2772 on a panel of 1280x2772`、`CRASH:` 0、无内核 panic。
- 主屏正常：23 个图标、Dock 4 个、搜索胶囊、壁纸 `(50,49,127)`、Dock `(45,45,45)`。
- 这一轮 `iconservicesagent` 仍是 CPU 路径，所以 `texture over buffer` 未被触发 —— 这是预期的：
  v93 只保证 `-buffer` 有答案，不改变谁在画。

## 4. v94：把 iconservicesagent 放回 GPU

v77 让它画 CPU 的理由是「weak 引用不是我们的 MTLDevice」（v87 在纹理已经 retain device 之后
仍 `SIGNAL 5`）。上游的根因说明那个 weak 引用其实是 **buffer**，而 buffer 当时恒为 nil。
v93 修好了它，所以这一步值得重试。

`checkenv_or_name()` 改为默认返回 0（GPU），`REDWOOD_AGENT_CPU=1` 保留旧的 CPU 行为。
`REDWOOD_AGENT_GPU=1` 这个旧开关不再需要。

### 结果：不再崩溃，但画不对

`once-v94` 真机（`fastboot boot`）：

- **`iconservicesagent` 没有再 `SIGNAL 5`**，日志里出现 `commit 933 took 24 ms over 93 recorded
  works`、`fd draw calls 15000`、`rwa buffer: copied 0x156820000 of 62464 bytes` ——
  它确实在 GPU 上画，buffer 纹理的写回也在跑。**v77 那条「weak 引用不是我们的 MTLDevice」
  的判断被推翻了：就是 buffer。**
- 但桌面渲染不完整：日历图标只剩灰底红顶、日期数字丢失；时钟只剩指针、表盘消失；
  App Store 的 A 缺一块；Dock 里电话/信息的白色图标底丢失。
- `SpringBoard` 崩 2 次（`SIGNAL 5`，v93 是 0 次）。

结论：v94 只是证明「GPU 路径能跑」，**不是可用基线**，已回退到 v93。
剩下的不是崩溃问题，而是渲染契约：玻璃/图标的图层需要多级颜色附件视图
（`rw_attachment_level`）、按附件共同区域绘制、8 附件清屏掩码与逐附件清屏颜色、
`RG16Float` 导入、新建目标清零（`texture_start_zeroed`）这些配合，缺一个就会丢一层。
这正是上游 11-11 → 11-13 那一批工作的内容。

## 6. 不能照搬的

| 上游条件 | 为什么 |
|---|---|
| `darwin` / `darwin_var` 持久化、`ANNFS001` 双槽、`ubc_msync` 落盘 | warsaw 的 GPT 里没有这两个分区，落盘通道无对象；跨开机缓存与亮度恢复只能用一半（同一次开机内跨 UID 共享仍成立） |
| TrollStore / `/private/var` 跨重启 | 依赖已写分区与持久化 |
| 画布 1206×2622、面板 1156×2510 | 我们是 1280×2772，任何按像素重算的表与 DPU 配置都要重算 |
| `k90auto` 的开关（`DIRTY_REGIONS` / `ICON_METAL` / `JOB_ENV`） | 那是它的打包器；我们要落到自己的 `build.sh` / payload 脚本 |
| 板级中断号与寄存器（INTID 336/297/206/261/240、DPU 直扫、`GPIO_86` TE） | SM8750 + K90 板级，warsaw 不同 |
| `var_apfs=1` 接管 `/private/var`、minicrypto 硬件密码学 | 上游自己判定未收敛；后者会 EL1 非法指令打死整机 |

## 7. 下一轮

**最优先：把 GPU 图标路径画对。** v94 已经证明它能跑、不崩，缺的是图层正确性：

1. `rw_attachment_level`：对 `level` 非 0 的颜色附件建该级纹理视图（当前所有通道都画进第 0 级，
   且每通道清屏把上一级清掉 —— 玻璃读到空模糊背景）。
2. 附件尺寸不一致时按所有附件的共有区域绘制，而不是拒绝整轮。
3. 8 附件清屏掩码与逐附件清屏颜色（`PIPE_CLEAR_COLOR0 << i`、动态 `colormask`）；
   只传首个附件颜色会把后面几个写成不透明黑 —— 这正是 widget 黑底/白块的形态。
4. `RG16Float`（`2C0h`）/ `OneComponent16Half`（`L00h`）格式导入、`texture_start_zeroed`。
5. 顺带查 SpringBoard 那 2 次 `SIGNAL 5`：v93（CPU 图标）是 0 次，可能与图标纹理的
   buffer 写回时序有关（写回发生在 fence 之后，而 SpringBoard 读得更早）。

**然后**：

6. **内核显示三件套**（纯内核、零 AIR 依赖）：`MiniFramebufferScale.h` 的 `same4()` 相同行
   快速路径；`MiniFramebufferRows.inc` 的 8 路哈希（`ROWS_UNHASHED 6 → 16`）；仅
   `changed_rows > 0` 才写背光脉冲。
7. **AIR**：让 Mesa CI 用修好 hunk 的 `0016` 重编；再考虑 `air_llvm.inc` 的 minnum/maxnum 与指针槽。
8. **性能**：停掉 `sb26_fill_all_icons` 每轮 23 个图标全量重填（上游指出只按 `displayName`
   计数会把「没画」当「画了」，且与原生 `updateImageAnimated:` 的 delayed/断言状态机打架）；
   `com.apple.iconservices` 冷超时分档（冷 key 60–100 ms，热 key 即时返回，必须永远返回可解码字典）。
